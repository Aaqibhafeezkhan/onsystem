# onsystem (formerly @dgesteves/design-system-mcp)

## 0.7.0

### Minor Changes

- [#107](https://github.com/dgesteves/onsystem/pull/107) [`9ecb46d`](https://github.com/dgesteves/onsystem/commit/9ecb46d7de5eea5ab5c259e0228ad5bc6cdafb35) Thanks [@dgesteves](https://github.com/dgesteves)! - Zero config now finds color tokens kept in a shared Tailwind config package, as Dub keeps them in `packages/tailwind-config`: it follows the `@import`s of the stylesheets it finds, by a path or into a workspace package (`@import "@acme/theme"` in Tailwind v4), reads presets that a package exposes only through `exports`, takes the stylesheets of a shared preset's package that set the colors its config maps, and reads bare RGB channels (`--content-error: 220 38 38`) as colors where the config reads them with `rgb()`.
  
  Upgrading from 0.6.0: a project that keeps its color tokens in such a package got no color findings from 0.6.0, which said "No color tokens found: no-hardcoded-color did not run". Now the rule runs and reports the colors it skipped: in Dub's `apps/web`, 10,024 errors and 164 warnings that a baseline written with 0.6.0 does not hold, so `check` exits 1 there. Run `onsystem check . --update-baseline` once after upgrading to accept them; in Dub the 1,052 findings 0.6.0 recorded still match, and `check` exits 0 again. The warnings are colors whose hue has no token in the theme, and they do not fail `check` unless you set `--max-warnings` (or `fail-on: warning` in the Action). The GitHub Action at `@v0` moves to each release when it is published, so pin it to a commit SHA if you need a stable check, and move the pin when you update the baseline.

- [#170](https://github.com/dgesteves/onsystem/pull/170) [`57aef3b`](https://github.com/dgesteves/onsystem/commit/57aef3bfe57904181334b2e4244415208d1af2ed) Thanks [@dgesteves](https://github.com/dgesteves)! - `check --prune-baseline` drops the baseline entries that no longer occur and accepts nothing new, and it is the command `check` now prints when baselined findings get fixed. The command it printed before, `--update-baseline`, also recorded every new finding of the run, so following it next to a new error accepted the error. The printed command keeps `--baseline`, `--root`, `--config`, `--components`, `--tokens`, `--docs`, `--include-design-system` and `--include-tests`, so it rewrites the same file from the same findings; before, with `--baseline <file>` it wrote a second baseline at the root. `--update-baseline` creates the baseline's folder, and with `--format json`, `sarif` or `github` prints its summary on stderr, so stdout stays in the format.
  
  The baseline now records the onsystem version that wrote it and the rules that ran. When a rule that did not run then reports findings, as when an upgrade finds tokens an older version missed, `check` says they are new to the baseline rather than to the code, and how many other new findings `--update-baseline` would accept with them. A baseline without these fields is read as before, and older versions of onsystem read the new ones without complaint.

- [#147](https://github.com/dgesteves/onsystem/pull/147) [`a19115d`](https://github.com/dgesteves/onsystem/commit/a19115df16b5dbfbc6a378ae80b6b87c7390a07c) Thanks [@dgesteves](https://github.com/dgesteves)! - `no-hardcoded-color` no longer offers two kinds of fix that changed what a color means, which `eslint --fix` and `applyFixes` applied unasked. A class under a condition (`hover:`, `focus-visible:`, `md:`) is not fixed to the token the same class list has or gets without it, nor the other way round, unless the two already have exactly the same color: `bg-[#2563eb] hover:bg-[#1d4ed8]` with a blue `primary` became `bg-primary hover:bg-primary`, and the button lost its hover. A slight change counts too: `bg-[#fff] hover:bg-[#fafafa]` keeps its hover. The base class is still fixed, and the message suggests keeping the two apart, such as with `hover:bg-primary/90`; `dark:` classes still get the same token, and so do two hardcoded classes of exactly the same color (`border-red-500 focus:border-red-500`), whose condition changed nothing before either, and classes for a pseudo-element or other elements (`placeholder:`, `prose-a:`, `[&_svg]:`). A fix to a token that is not a status color is held back when a status color of the color's hue is close too and at most ΔE 0.03 further: with a rose `brand` next to a red `destructive`, `bg-[#ef4444]` on a payment-failed alert became `bg-brand`, so the error would follow the next rebrand. The message now offers both (`bg-destructive` if the color shows a status, otherwise `bg-brand`). The brand's own color, and reds that `destructive` matches, are still fixed.

- [#141](https://github.com/dgesteves/onsystem/pull/141) [`a83de7c`](https://github.com/dgesteves/onsystem/commit/a83de7c55ce368be14f0e4f38b132e7aa8634a42) Thanks [@dgesteves](https://github.com/dgesteves)! - `no-hardcoded-color` counts opacity when it matches a color to a token. It used to compare only lightness, chroma and hue, so a translucent color matched its opaque token and the fix made it opaque: `bg-[#e7000b33]` (the red at 20%) became `bg-destructive`, `rgba(255, 255, 255, 0)` became the opaque background, and in shadcn/ui's dark theme `dark:border-[#ffffff]` became `dark:border-border`, which is 10% white. Now a token more than 0.02 apart in opacity is never a fix, and the message gives both opacities (`destructive is opaque, and this color is 20% opaque.`), so the color can keep its opacity with a modifier (`bg-destructive/20`). Colors and tokens of the same opacity still match (`dark:border-[rgba(255,255,255,0.1)]` → `dark:border-border`, and 15% white → `dark:border-input`), an opacity modifier still stays on the token (`bg-[#ffffff]/40` → `bg-background/40`), and "same value as" lists only tokens of the same opacity.

- [#138](https://github.com/dgesteves/onsystem/pull/138) [`2633d3f`](https://github.com/dgesteves/onsystem/commit/2633d3f7ff34ca10df9742f442e5e604f821e193) Thanks [@dgesteves](https://github.com/dgesteves)! - `no-unknown-prop` and `no-unknown-variant` no longer fix a guess that changes what the code means. `eslint --fix`, fix-on-save and the agent tools applied them: `<Button href="/docs">` became `ref="/docs"`, `<Input onValueChange={…}>` became `onVolumeChange`, `as="a"` and `component={Link}` became `asChild`, `onClose` became `onOpenChange` (which also runs on open), and `size="xl"` on a button with an `xs` size became `xs`.   - A prop guessed by spelling from the attributes a component forwards is named in the message but not fixed (`disable`: Did you mean "disabled"?). `ref`, whether the component forwards it or takes it as its own prop, and forwarded event handlers are never guessed by spelling.
