The MCP tools answer better where the design system is thin, large, or has no component for what the agent wants.

- `search_components` says when no component clearly matches: "a dropdown menu to pick a country" in a design system with no select used to come back as `CardAction`, best first, because its description mentions a menu. A result now matches clearly when a word of the query is in its name, or when it has more than half of the query's words (itself or through a synonym). When some do, the others are left out; when none does, the answer starts "No component clearly matches", lists the nearest and marks each result `weak: true` in the structured content.
- A shadcn/ui component without JSDoc, laid out as `npx shadcn add` writes it (`Badge` in `components/ui/badge.tsx`: the file named for it, in a `ui` folder), is described by what shadcn/ui's component of that name is for, said as shadcn/ui's (`shadcn/ui's Badge: A small label for a status, a count or a category.`), in `list_components`, `get_component`, resources and the search index, so "status label" finds Badge first in a stock app. A component of the same name elsewhere, such as a design system's `src/sheet.tsx`, gets no borrowed description. A component with no description is listed without one, not as "No description."
- `list_components` takes `query`, `kind` (`"component"` or `"icon"`) and `limit`. Icons, the components that render an `<svg>`, are named on one line when there are five or more from one import, or from one folder for an icon set with a module per icon (`components/icons/check.tsx`, each named with its module), instead of one entry each, in the text and in the structured content, which has them under `icons` and leaves out empty `variants` and `subcomponents`. `kind: "icon"` lists them one by one.
- `get_component` lists the parts before the props, cuts a prop's description longer than 160 characters to its first sentence (the structured content keeps it all), and says so when the name asked for is not how the design system writes it: `Card.Header` answers with CardHeader and "There is no `Card.Header` in this design system: write `<CardHeader>`."
- `get_tokens` lists chart and sidebar colors (and other families one part of the UI uses) under their own headings, after the other colors: `## chart (5): for charts only, not for status colors`. The server instructions and the `build-with-design-system` prompt say what to do for a status color the theme has no token for: add a token or keep the Tailwind color as `check_ui` says, and never use a `chart-*` or `sidebar-*` token for it. The prompt no longer asks the agent to follow examples a component does not have.
- `check_ui` with `code` takes a `path` to a .tsx, .jsx, .ts or .js file as the file the code is for, as `filename`: it was ignored, so the code was checked as `snippet.tsx`, without the `overrides` for that file. Any other `path`, such as a project folder, picks the project at a monorepo root, and the code is still checked as `snippet.tsx`. A `filename` that is not a script file says to pass the .tsx path the code is for, or to leave it out.
- Library API: `searchComponents` and `DesignSystem.search` follow the same floor. When some results match clearly, they return only those, so a query can return fewer results than before; when none does, they return the nearest, each with `weak: true`.
