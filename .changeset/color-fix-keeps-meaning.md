`no-hardcoded-color` no longer offers two kinds of fix that changed what a color means, which `eslint --fix` and `applyFixes` applied unasked. A class under a condition (`hover:`, `focus-visible:`, `md:`) is not fixed to the token the same class list has or gets without it, nor the other way round: `bg-[#2563eb] hover:bg-[#1d4ed8]` with a blue `primary` became `bg-primary hover:bg-primary`, and the button lost its hover. The base class is still fixed, and the message suggests keeping the two apart, such as with `hover:bg-primary/90`; `dark:` classes still get the same token. A fix to a token that is not a status color is held back when a status color of the color's hue is close too and at most ΔE 0.03 further: with a rose `brand` next to a red `destructive`, `bg-[#ef4444]` on a payment-failed alert became `bg-brand`, so the error would follow the next rebrand. The message now offers both (`bg-destructive` if the color shows a status, otherwise `bg-brand`). The brand's own color, and reds that `destructive` matches, are still fixed.
