---
'onsystem': minor
---

An app on a design-system package installed from a registry as compiled `dist/` and type declarations alone now gets every rule: its components, props, variant values, parts and the elements they render are read from its `.d.ts` files, as MUI's are. Before, such an app got the token rules and `check` said `No design-system components found: the component rules did not run.` This applies to a package that declares its onsystem config (set up with `init`), whatever its name, and to one without a config that is named like a design system in the app's own npm scope (`@acme/ui` for `@acme/web`). A kit from another scope named like one (`@sanity/ui`, `@react-email/components`) is not read, and a package that publishes its `.tsx` sources is read from them as before. `inspect` lists it on its `library` line (`Design-system package (@acme/ui 1.0.0): 10 components from its type declarations`), `inspect --explain` says so, `"libraries": false` turns it off, and the app's `@import` of its stylesheets brings its tokens.

Reading declarations also got more exact for MUI and any package: a capitalised export is a component only when it renders (a function returning a string, or a class without `render`, is not); variants that tsup inlines with cva's `ClassProp` are kept, since its `class-variance-authority/dist/types` import now resolves by path when the app's `"moduleResolution": "bundler"` does not; a function component's element comes from its DOM attributes when it takes no `ref`; props that depend on a generic `component` through a conditional type are left open, so they are not reported as unknown; and `Tabs` next to `Tab`, or a lone `CheckboxGroup` next to `Checkbox`, is no longer taken for its part.
