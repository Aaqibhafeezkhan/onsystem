# Rules

Eight rules, the same in `check_ui`, `onsystem check` and the Claude Code hook. Every finding has a rule id, a location and a message that says what to write instead; most carry a fix as text edits. When a fix renames a tag to a component the file does not import yet (`<button>` to `<Button>`), the message names the import to add, and the [ESLint plugin](eslint.md) offers that rename as a suggestion rather than a fix, so `eslint --fix` never writes a component the file does not import or declare. The [rules catalog](https://onsystem.vercel.app/rules) on the website shows each one on a real example.

## How fixes are chosen

Color matches under ΔE 0.02 count as the same color. Under 0.1 the fix is offered, except for a Tailwind palette class: it is fixed only to a token that matches it or that is nearest to the class's own shade (of the shades in its family) and within ΔE 0.037 of it, the most Tailwind v3 and v4 differ on one shade. Another close token is suggested without a fix, and the message says why (one shade darker, or closest to another color of the same shade). Beyond 0.1 the message names the nearest token but leaves the choice to the agent. Opacity is part of the color: a token more than 0.02 apart in opacity is never a fix, so `bg-[#e7000b33]` (the red at 20%) is not fixed to an opaque `bg-destructive`, nor `dark:border-[#fff]` to a dark `border` that is 10% white. The message gives both opacities, and an opacity modifier stays on the token (`bg-[#fff]/40` → `bg-background/40`). A fix is only offered for a token of the same hue (within 15°), or a gray for a gray, whether the color is a palette class, an arbitrary value or a literal: a pale color counts as a hue by its chroma relative to its lightness, so `bg-[#fef2f2]` is never swapped for a light gray that happens to be close. Status colors (`destructive`, `warning`, `success`, `info` and their foregrounds) are only offered for nearly the same hue (within 8°), never for a gray, so a brand-orange button does not become `bg-destructive`. The other way round, a fix to another token is held back when a status color of the color's hue (within 15°) is close too and at most ΔE 0.03 further: next to a rose `brand`, `bg-[#ef4444]` may be an error, so the message offers `bg-destructive` if the color shows a status and `bg-brand` otherwise, and error text does not follow the next rebrand. When a color is a hue and no token has it, the finding is a warning that names no token: add a token for the hue, or keep the color with a suppression comment and a reason (`{/* */}` between JSX children). Among the tokens that qualify, the one made for the utility wins: `foreground` and `muted-foreground` for `text-*`, `fill-*` and `stroke-*`; surfaces such as `muted` for `bg-*`; `border`, `input` and `ring` for `border-*` and `ring-*`. Tokens named `on-*` are text colors, and so are `content-*` tokens unless the rest of the name says border or background (`content-border`, `content-background`). A close token made for another role is named in the message but never swapped in. `sidebar-*` and `chart-*` tokens are only suggested in a sidebar or a chart (by file, enclosing component or classes), and so is any other family that at most one design-system file uses, such as syntax-highlighting colors or one screen's background, outside that file's components; `dark:` classes are compared with dark-mode values. A class under a condition (`hover:`, `focus-visible:`, `md:`) is not fixed to the token the same class list has or gets without it, nor the other way round, unless the two already have exactly the same color: `bg-[#2563eb] hover:bg-[#1d4ed8]` would become `bg-primary hover:bg-primary`, and the hover would change nothing. The message suggests keeping them apart (`hover:bg-primary/90`). `dark:` is not such a condition: a `dark:` class is compared with dark-mode values, so the same token there is a fix. Nor is a variant for a pseudo-element or other elements (`placeholder:`, `*:`, `prose-a:`, `[&_svg]:`), whose color the class without it does not set. Two hardcoded classes of exactly the same color (a palette class and its hex count as one) keep their fixes too, since the condition changed nothing before either: `border-red-500 focus:border-red-500` keeps an error border red on focus. A slight change is still a change: `bg-[#fff] hover:bg-[#fafafa]` keeps its hover, though both are within 0.02 of `background`. A state class is compared with the class it starts from: a `dark:hover:` class with the list's `dark:` class, when there is one.

Likewise, a spacing or radius step that is off by more than half the value (and more than 4px) is suggested but not auto-fixed. Rules that need tokens are skipped when the design system defines none of that category; a stylesheet that imports `tailwindcss` brings Tailwind's default spacing unit and radius scale, unless the theme resets that namespace (`--spacing-*: initial`, `--radius-*: initial`), in which case only the project's own steps are suggested. Syntax errors are reported as `syntax`, and so is code nested too deeply for TypeScript's parser (thousands of levels), which is then not checked.

An icon button's label is fixed only when the icon means one thing on a button (a trash can, pencil, magnifier, gear, copy, download, upload, share or filter icon, named plainly: `Trash2` or `TrashIcon`, not `Binary` or `FilterX`) or the code says what the button does: "More options" on a menu's trigger, and for an X, "Close" in a close part (`DialogClose`) whatever its `onClick` calls, or elsewhere "Remove", "Clear" or "Close" when every function its `onClick` calls says that one action (`removeAssertion(index)`, `clearSearch()`, `setOpen(false)`; `clearTimeout` does not count). Otherwise the message names a label without a fix, since a plus may add or expand, a chevron go to the next page or expand a row, and an X close, remove or clear: an X that resets a form and closes (`form.reset(); setOpen(false)`) is named "Close", and one that calls `closeDeleteDialog` or `onCancelDelete`, or acts only in a callback such as `onSuccess`, is named without a fix. A chevron or arrow in a collapsible's or accordion's trigger, or on a button with `aria-expanded`, `data-state` or `data-[state=open]:` classes, is named "Toggle", not "Next" or "Previous".

## Suppressing findings

A comment turns rules off where a finding is intended, and says why after `--`:

```tsx
// onsystem-disable-next-line no-hardcoded-color -- the brand's exact orange
<Button className="bg-[#ff6b00]">Sign in</Button>

<p className="text-[#737373]" /> // onsystem-disable-line no-hardcoded-color

{/* onsystem-disable-next-line no-hardcoded-color, no-hardcoded-spacing */}
<div className="bg-[#0a0a0a] p-[13px]" />
```

`onsystem-disable-next-line` covers the next line, `onsystem-disable-line` its own, and `/* onsystem-disable */` the rest of the file (at the top, the whole file). Without rule names they turn every rule off. A misspelled rule name is reported as a `suppression` warning, with the closest one, and suppresses nothing; syntax errors cannot be suppressed. For whole folders or kinds of files, such as legacy screens or generated code, use `overrides` in the [config](configuration.md#config-file).
